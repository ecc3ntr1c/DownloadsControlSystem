# DownloadsControl

**Демоверсия · 0.1.0**

DownloadsControl — корпоративный портал для получения стороннего ПО. Сотрудник подаёт заявку с прямой ссылкой на файл и объясняет, зачем он нужен. Сервис скачивает файл в карантин и проверяет его антивирусами. Сотрудник информационной безопасности (ИБ) изучает отчёты и принимает решение. После согласования владелец заявки скачивает файл через портал.

Демоверсия показывает весь маршрут от заявки до выдачи, включая отказ, аудит, уведомления и очистку файлов по сроку хранения. Сотрудник начинает работу с ввода имени, а ИБ входит под отдельной учётной записью. Ограничение самостоятельных интернет-загрузок сотрудников обеспечивает корпоративная инфраструктура. Сквозная авторизация через Active Directory запланирована отдельно. Интеграции с 1С и SMTP, установка ПО, инвентаризация и управление лицензиями выходят за рамки демоверсии.

## Первый запуск

Нужны запущенный Docker Desktop или Docker Engine с Compose, поддерживающим `volume.subpath`, и Python 3 на хосте. Для первой сборки нужны доступ к реестрам образов и репозиториям зависимостей, для ClamAV — доступ к обновлениям баз. Выделите Docker около 4 ГиБ памяти. Python приложения (3.14) и Poetry уже входят в сборку контейнера.

Из корня проекта выполните:

```sh
docker compose version
docker info --format '{{.ServerVersion}}'
python3 scripts/init_compose_env.py
docker compose --env-file .env.compose up --build -d --wait --wait-timeout 360
docker compose --env-file .env.compose ps -a
```

Скрипт создаёт `.env.compose` с отдельными секретами и правами `0600`. Если файл уже существует, используйте его и начните с команды `up`. Compose по умолчанию запускается как проект `downloadscontrol-v1`. Одноразовый контейнер `setup` выполняет миграции, создаёт группы и каталоги, собирает статику и штатно завершается с кодом `0`.

Проверьте готовность и создайте суперпользователя. Команда спросит имя пользователя, электронную почту и пароль.

```sh
curl -fsS http://127.0.0.1:8080/readyz/
docker compose --env-file .env.compose exec app python manage.py createsuperuser
```

Ожидаемый ответ проверки — `{"status": "ready"}`. Этот адрес проверяет связь Django с PostgreSQL и Redis и структуру хранилища. Готовность ClamAV смотрите отдельно в выводе `docker compose ps -a`. Порт портала можно задать через `PORTAL_PORT` в `.env.compose`. Если меняете порт, используйте его во всех адресах ниже.

## Роли и интерфейс

| Роль | Что доступно | Где работать |
| --- | --- | --- |
| Сотрудник | Вводит имя при первом входе, подаёт заявки, видит свои заявки и уведомления, скачивает выданные ему файлы. Группа `SoftwareControl_Users` используется для организационного учёта | [Мои заявки](http://127.0.0.1:8080/), [Уведомления](http://127.0.0.1:8080/notifications/) |
| `SoftwareControl_Security` | Просматривает очередь и отчёты, согласует выдачу, отказывает и повторно запускает обработку подходящих заявок | [Очередь ИБ](http://127.0.0.1:8080/security/) |
| `SoftwareControl_Admins` | Получает те же три права ИБ — просмотр, согласование и отказ. Повтор использует право согласования. Права Django Admin назначаются отдельно | [Очередь ИБ](http://127.0.0.1:8080/security/) |
| Суперпользователь Django | Создаёт аккаунты, назначает группы, настраивает политики и антивирусы, просматривает служебные записи | [Администрирование](http://127.0.0.1:8080/admin/) |

Сотруднику ИБ достаточно обычного активного аккаунта с группой `SoftwareControl_Security`. Для доступа к Django Admin требуются `is_staff` и права на нужные модели. Настройка антивирусных подключений доступна суперпользователю.

### Первый вход сотрудника

Портал перенаправляет посетителя без сессии на `/welcome/`. После отправки имени Django создаёт отдельную служебную учётную запись без доступного пароля и привилегий. Cookie содержит идентификатор сессии, а сервер хранит сессию и ID пользователя. Имя показывается на портале и в очереди ИБ. Владельцем заявки считается уникальная учётная запись, поэтому одинаковые имена в двух браузерах дают доступ к разным заявкам.

При повторном посещении с действующей cookie имя вводить заново не нужно. После выхода, окончания сессии, очистки cookie или перехода в другой профиль браузера повторный ввод имени создаёт новую учётную запись. Прежние заявки остаются в истории ИБ. Для входа ИБ и существующих локальных пользователей на странице есть ссылка **Войти с учётной записью** (`/login/`).

## Ручная проверка через браузер

### 1. Создайте учётную запись ИБ

1. Войдите в [Django Admin](http://127.0.0.1:8080/admin/) под суперпользователем. Откройте **Пользователи → Добавить**.
2. Создайте активного пользователя с паролем, например `security_demo`. В его карточке добавьте `SoftwareControl_Security` в выбранные группы и нажмите **Сохранить**.
3. Используйте отдельные профили браузера или разные браузеры для сотрудника и ИБ. Оставьте сессию сотрудника открытой до конца теста.

### 2. Подайте заявку

1. В чистом профиле откройте [портал](http://127.0.0.1:8080/), введите имя, например `Иван Петров`, и нажмите **Продолжить**. На странице **Мои заявки** нажмите **Новая заявка**. Форму можно открыть напрямую по адресу `/requests/new/`.
2. Введите в поле **Прямая ссылка на файл** адрес небольшого публичного текстового файла. Для примера подойдёт [RFC 20](https://www.rfc-editor.org/rfc/rfc20.txt) по адресу `https://www.rfc-editor.org/rfc/rfc20.txt`. Контейнеру worker нужен сетевой доступ к этому источнику.
3. Заполните **Название и описание ПО** значением `RFC 20, демонстрационный текстовый файл`, а **Для какой задачи нужно ПО** — `Проверка маршрута согласования и выдачи`. Нажмите **Подать заявку**.
4. Запишите номер заявки. В состоянии появится **На автоматической обработке**. Пока обработка идёт, нажимайте **Обновить статус** или обновляйте страницу. Кнопка скачивания появится после согласования.

### 3. Согласуйте выдачу и скачайте файл

1. В другом профиле откройте `/login/` и войдите как `security_demo`. Откройте **Очередь ИБ**, найдите заявку по номеру и дождитесь статуса **Ожидает решения ИБ**.
2. В блоке **Результаты проверки** сверьте имя, размер, тип и SHA-256 файла. Для успешного сценария ClamAV должен показать **Чистый**.
3. В блоке **Действия ИБ** нажмите **Разрешить выдачу**. При обычном согласовании комментарий можно оставить пустым. Если карточка показывает совпадение с правилом, допускающим исключение, укажите обоснование в поле **Комментарий ИБ**.
4. Вернитесь в сеанс владельца и обновите карточку. Проверьте статус **Доступна для скачивания**, кнопку **Скачать файл**, срок выдачи и уведомление о решении.
5. Скачайте файл. После первого разрешённого GET карточка покажет **Файл выдан пользователю**. Ссылка работает в сеансе владельца до конца срока хранения. Для проверки прав откройте новый профиль, введите то же имя сотрудника и откройте ссылку на скачивание. Ожидается HTTP 404.
6. Под суперпользователем откройте **Журнал аудита** в Django Admin. Найдите события `REQUEST_CREATED`, `SCAN_COMPLETED`, `REQUEST_APPROVED` и `FILE_DOWNLOAD_AUTHORIZED` для номера заявки. Последнее событие фиксирует разрешение GET-запроса сервером.

### 4. Проверьте отказ и блокировку выдачи

1. Подайте вторую заявку с той же ссылкой. После обработки откройте её как `security_demo`.
2. Введите `Демонстрационный отказ` в **Комментарий ИБ** и нажмите **Отказать**. Проверьте у владельца статус **Отказана ИБ**, причину, уведомление и отсутствие кнопки скачивания.
3. Для проверки автоматического блокирования создайте третью заявку на HTML-страницу, например `https://www.rfc-editor.org/`. Стартовая политика запрещает HTML. В карточке ИБ ожидается ошибка автоматической обработки с доступным отказом и без действия **Разрешить выдачу**.
4. При временной ошибке исправьте её причину и нажмите **Повторить обработку**, если действие доступно в карточке. Повтор сбрасывает незавершённую проверку, возвращает заявку в очередь и сохраняет событие `REQUEST_REPROCESSING`. Выполненное решение ИБ закрывает возможность повторной обработки этой заявки.

## Как принимается решение

1. **Приём.** Портал и REST API вызывают `SoftwareRequestService`. В PostgreSQL в одной транзакции записываются заявка, источник и аудит. После фиксации задача отправляется в Redis. Если отправка временно недоступна, Celery Beat каждые 15 секунд ищет заявки, которые пора поставить в очередь.
2. **Правила и скачивание.** Worker захватывает заявку с блокировкой строки и временным токеном обработки. Сначала он сверяет ссылку, домен, описание и обоснование с активным реестром запрещённого ПО. Жёсткий запрет останавливает процесс до скачивания. Затем скачиватель проверяет адрес, порт, DNS/IP и каждое перенаправление, ограничивает объём, определяет тип, вычисляет SHA-256 и сохраняет файл в карантине.
3. **Антивирусы.** Перед сканированием применяются политики типов файлов. Worker сохраняет список назначенных провайдеров. ClamAV проверяет поток локально, а удалённые адаптеры отправляют файл в настроенный сервис и опрашивают отчёт по ID. Сохраняются вердикт, хеш, резюме и подробности. По завершении проверки или после окончательного сбоя заявка переходит в **Ожидает решения ИБ**. Статус **Проверка завершена** описывает завершение этапа. Вердикт каждого провайдера виден отдельно.
4. **Согласование.** Веб-форма и API вызывают один `ApprovalService`, который повторно проверяет право ИБ и состояние заявки под блокировкой. Для выдачи требуется файл этой заявки в карантине с действующим сроком хранения. Каждый назначенный провайдер должен вернуть чистый результат для того же файла и SHA-256. Сервис проверяет совпадения с реестром и актуальную политику типа файла. Ошибка, подозрительный или неизвестный вердикт и прежний имитационный `MOCK` блокируют выдачу.
5. **Публикация или отказ.** При согласовании сервис копирует файл в `approved` и проверяет SHA-256 перед публикацией. При отказе комментарий обязателен, а файл по возможности переносится в закрытую зону `rejected`. Решение, время, автор, комментарий, аудит и уведомление фиксируются вместе. После согласования исходная копия удаляется из карантина при успешной фиксации изменений.
6. **Выдача и очистка.** При каждом скачивании Django проверяет текущую сессию, владельца, связь файла с заявкой, решение и срок. В Compose Django передаёт Nginx внутреннее указание `X-Accel-Redirect`, а Nginx выдаёт файл вложением. После дедлайна ссылка сразу перестаёт работать. Периодическая задача каждые пять минут проверяет сроки, удаляет истёкшие файлы и сохраняет историю. Выданная заявка с истёкшим сроком переходит в **Закрыта** после очистки.

## Политики и настройки

Через Django Admin доступны **Политики скачивания**, **Защитные правила скачивания**, **Политики типов файлов**, **Реестр запрещённого ПО** и **Подключения антивирусов**. Карточки заявок, источников, файлов и результаты проверок доступны там для просмотра. Согласование выполняется из очереди ИБ или через её API.

- **Политика скачивания.** На чистой базе разрешены прямые HTTP(S)-ссылки на портах 80 и 443, включая перенаправления на CDN, с лимитом 50 МиБ. Локальные и служебные адреса и HTML блокируются. Частные адреса требуют явного допуска и списка доверенных доменов.
- **Защитные правила скачивания.** Определяют, как обрабатывать источники, требующие доступа или авторизации.
- **Политики типов файлов.** Сопоставляют расширение и MIME-тип, применяют допуск и размер. Требование отдельной распаковки или песочницы блокирует выдачу в демоверсии.
- **Реестр запрещённого ПО.** Совпадения фиксируются при обработке. Для допустимого исключения в правиле должны быть включены **Требует подтверждения ИБ** и **Разрешить ИБ игнорировать правило**. При согласовании такого исключения комментарий обязателен, а его автор и время сохраняются.
- **Антивирусы.** ClamAV включён по умолчанию. Суперпользователь может добавить VirusTotal или HTTPS-шлюз другого антивируса. Настройка, передача образцов и контракт шлюза описаны в [документации по антивирусам](docs/antivirus.md).
- **Хранение.** Значения по умолчанию — 14 дней в карантине, 30 после согласования, 7 после отказа. Они задаются через `QUARANTINE_RETENTION_DAYS`, `APPROVED_RETENTION_DAYS` и `REJECTED_RETENTION_DAYS`. При запуске вне Compose настройки Django читают локальный `.env`.

## REST API

| Метод и путь | Действие |
| --- | --- |
| `POST /api/v1/requests/create/` | Создать заявку. Поля `source_url`, `description`, `business_reason` |
| `GET /api/v1/requests/`, `GET /api/v1/requests/{id}/` | Свои заявки, состояние и `download_url` при доступности |
| `GET /api/v1/security/requests/`, `GET /api/v1/security/requests/{id}/` | Очередь ИБ, данные о файле, отчёты и причины блокировки |
| `GET /api/v1/security/requests/{id}/scans/{scan_id}/` | Подробный отчёт для ИБ |
| `POST /api/v1/security/requests/{id}/approve/` | Разрешить выдачу. `security_comment` обязателен для исключения из реестра |
| `POST /api/v1/security/requests/{id}/reject/` | Отказать с обязательным `security_comment` |
| `POST /api/v1/security/requests/{id}/reprocess/` | Повторить обработку, если состояние заявки допускает повтор |
| `GET /downloads/{id}/` | Скачать файл в сеансе владельца. Здесь `id` — ID файла |
| `GET /healthz/`, `GET /readyz/` | Проверить HTTP и готовность PostgreSQL, Redis и хранилища соответственно |

REST API принимает Django-сессию с CSRF для изменений или HTTP Basic. Эндпоинт скачивания использует Django-сессию. Интерактивное описание доступно в [Swagger](http://127.0.0.1:8080/api/docs/), схема — по адресу `/api/schema/`.

## Автоматические проверки

### Локальные тесты

Для запуска на хосте нужны Python 3.14, Poetry и системная библиотека `libmagic` (на macOS её можно установить командой `brew install libmagic`).

```sh
poetry install --no-root
poetry run python manage.py test --settings=config.test_settings --noinput
poetry run python manage.py makemigrations --check --dry-run --settings=config.test_settings
poetry run python manage.py spectacular --validate --fail-on-warn --settings=config.test_settings --file /dev/null
```

Тесты используют SQLite в памяти, временное хранилище и брокер в памяти. Ответы внешних сервисов подменяются в тестах. Проверка конкурентной обработки требует PostgreSQL и штатно пропускается в режиме SQLite.

### Сквозной тест в Compose

Этот сценарий использует локальный текстовый файл `deploy/fixtures/package.txt`. Он проходит через Nginx, PostgreSQL, Redis, Celery и реальный ClamAV и использует отдельный проект, секреты, тома и порт `18080`. Если `.env.smoke` уже есть, используйте его повторно.

```sh
python3 scripts/init_compose_env.py --smoke .env.smoke
docker compose --env-file .env.smoke -p downloadscontrol-smoke -f docker-compose.yml -f deploy/compose.smoke.yml up --build -d --wait --wait-timeout 360
docker compose --env-file .env.smoke -p downloadscontrol-smoke -f docker-compose.yml -f deploy/compose.smoke.yml exec -T app python -m scripts.compose_smoke
docker compose --env-file .env.smoke -p downloadscontrol-smoke -f docker-compose.yml -f deploy/compose.smoke.yml exec -T -e TEST_POSTGRES=1 app python manage.py test --settings=config.test_settings --noinput
docker compose --env-file .env.smoke -p downloadscontrol-smoke -f docker-compose.yml -f deploy/compose.smoke.yml down
```

Скрипт создаёт аккаунт ИБ и открывает две демонстрационные сессии с одинаковым именем. Он проверяет чистый отчёт ClamAV и его SHA-256, согласование через API, выдачу правильных байтов владельцу, HTTP 404 для одноимённой чужой сессии, аудит, истечение срока и очистку. После успешного запуска скрипта этот же стенд можно использовать для ручного теста по адресу `http://127.0.0.1:18080/`. Создайте суперпользователя командой `exec app python manage.py createsuperuser` с теми же аргументами Compose и следуйте ручному сценарию до остановки стенда. Для положительного сценария и отказа используйте `http://fixture.test:8000/package.txt`, для проверки блокировки HTML — `http://fixture.test:8000/`.

## Диагностика и остановка

```sh
docker compose --env-file .env.compose ps -a
docker compose --env-file .env.compose logs --tail=100 setup app worker scheduler clamav nginx
docker compose --env-file .env.compose down
```

- Если `up --wait` завершился по таймауту, смотрите состояние `setup` и журналы `clamav`. При первом старте загрузка антивирусных баз может занять несколько минут. Когда она завершится, повторите `up` или проверьте готовность снова.
- Если порт занят, измените `PORTAL_PORT` в `.env.compose` и повторите запуск.
- Если заявка долго остаётся на автоматической обработке, смотрите журналы `worker`, `scheduler` и `clamav`. Если этап завершился ошибкой, откройте карточку ИБ и проверьте текст ошибки и отчёты.
- `down` останавливает стенд и сохраняет данные в именованных томах. Повторный `up` с тем же файлом окружения и именем проекта использует их снова.

Порядок работы с существующими данными, корпоративным HTTPS и резервными копиями описан в [архитектуре и эксплуатации](docs/architecture.md).

## Постоянный внутренний портал

Полноценный веб-интерфейс входит в этот же Compose-стенд. Django отдаёт страницы входа, заявок, очереди ИБ, отчётов и уведомлений, а Nginx обслуживает CSS и выдачу файлов. Для доступа коллег используйте внутренний адрес с HTTPS по схеме из [руководства по развёртыванию](docs/architecture.md#развёртывание).

Для режима с локальными учётными записями задайте `DEMO_NAME_LOGIN=0` в `.env.compose` и примените настройки через `docker compose --env-file .env.compose up -d`. Это отключает создание новых сессий по имени. Уже выданные демонстрационные сессии действуют до выхода или истечения срока. При переходе на Active Directory вход должен передавать подтверждённую доменную личность, а для связи пользователя с заявками понадобится стабильный идентификатор каталога. Внутренний веб-интерфейс при этом можно использовать дальше.
