# Архитектура и эксплуатация DownloadsControl

## Обработка заявки

1. `requests_app.services.SoftwareRequestService` в одной транзакции создаёт заявку, источник и запись аудита. После фиксации транзакции публикуется задача с ID заявки. Если Redis недоступен, заявка остаётся в PostgreSQL, а планировщик позже попробует поставить её в очередь.
2. `requests_app.processing` под блокировкой строки выдаёт обработчику ограниченное по времени право на работу. Токен проверяется перед изменением состояния. Дубли задачи не получают право параллельно обрабатывать одну заявку. После остановки worker планировщик восстанавливает работу по истечении этого времени. Для временных ошибок предусмотрено до трёх попыток.
3. Проверяется реестр запрещённого ПО. Запрет без исключения завершает автоматическую обработку до скачивания. Срабатывания, допускающие исключение, видны ИБ. Обычная политика источника применяется к исходному адресу и каждому перенаправлению.
4. Загрузчик пишет файл в закрытый временный каталог и вычисляет SHA-256. Сервис хранилища переносит файл в карантин. В БД сохраняются имя, тип, размер и хеш. Перед проверкой применяются правила типов файлов и размера.
5. Для файла создаются записи `ProviderScan` по включённым подключениям. ClamAV проверяет поток внутри локальной сети. HTTP-адаптеры отправляют файл в настроенный сервис и сохраняют ID для опроса. Вердикт, SHA-256, резюме и подробности хранятся в `ScanResult`. Ошибка и неполный ответ блокируют выдачу.
6. Заявка переходит в очередь решений ИБ после завершения или окончательной ошибки автоматической обработки. ИБ может отказать в любом из этих двух случаев. Разрешение требует чистых результатов всех назначенных антивирусов для конкретного файла, действующего срока хранения и отсутствия блокирующего правила.
7. При разрешении создаётся копия в зоне выдачи. Её хеш проверяется перед публикацией. Состояние файла, решение, аудит и уведомление фиксируются в одной транзакции. Карантинная копия удаляется после фиксации. При отказе файл переносится в закрытую зону отклонённых либо остаётся в карантине до очистки, если перемещение не удалось.
8. Ссылка на выдачу появляется в карточке владельца. Django проверяет сессию и доступ к конкретной заявке. В Compose он передаёт Nginx внутреннее указание `X-Accel-Redirect`. Nginx отдаёт файл как вложение. Прямое обращение к служебному пути возвращает 404. Счётчик и аудит регистрируют разрешённые GET-запросы.
9. С истечением срока Django перестаёт разрешать скачивание. Задача очистки удаляет файлы и временные остатки, сохраняет метаданные и аудит. Завершённая выдача переходит в статус «Закрыта».

## Компоненты

| Модуль | Ответственность |
| --- | --- |
| `config` | Настройки Django и Celery, подключение маршрутов, проверки работоспособности и готовности |
| `accounts` | Локальные аккаунты Django, ролевые права и начальная настройка групп |
| `requests_app` | Заявки, формы и REST API, очередь ИБ, согласованные переходы состояний, постановка и восстановление фоновой обработки |
| `files_app.downloaders` и `files_app.validators` | HTTP(S), проверка DNS/IP/порта и перенаправлений, ограничение потока и определение метаданных |
| `files_app.services.policies` и `review_policies` | Активная политика источников, правила типов файлов, реестр запрещённого ПО |
| `files_app.services.storage` | Имена, закрытые каталоги, переносы, проверка путей и контрольной суммы при публикации |
| `files_app.services.delivery` и `retention` | Авторизация выдачи, счётчик, сроки и очистка |
| `scanning` | Подключения и ключи в админке, адаптеры ClamAV, VirusTotal и HTTPS-шлюза, краткие и подробные результаты |
| `audit` | История действий. Рабочие записи доступны на просмотр в Django Admin |
| `notifications` | Внутренние уведомления и отметки прочтения |
| `integrations` | Резерв для корпоративных интеграций. Действующие интеграции используют имеющийся REST API |
| `templates` и `static` | Интерфейс сотрудника и ИБ без внешних ресурсов |
| `deploy` | Настройки ClamAV, Nginx и изолированной сквозной проверки |

Удаление файла сохраняет запись с SHA-256, решением и событиями аудита. Модели обработки, аудит и результаты сканирования доступны только для просмотра в админке. Решения проходят через сервис ИБ.

## Развёртывание

- Compose публикует один порт Nginx на `127.0.0.1`. PostgreSQL, Redis, ClamAV и Gunicorn доступны только соответствующим контейнерам. Nginx монтирует только зону `approved` для чтения. Карантин остаётся в файловом томе приложения с закрытыми правами.
- Для корпоративного доступа настройте HTTPS на существующем внутреннем прокси и направьте его на локальный порт Nginx. Укажите внешний домен в `ALLOWED_HOSTS` вместе с `127.0.0.1` для проверки готовности, выставьте `PORTAL_SCHEME=https` и при необходимости `CSRF_TRUSTED_ORIGINS=https://ваш-внутренний-домен`. Nginx выставляет доверенный протокол при обращении к Django. Сохраняйте привязку порта к loopback или ограничьте его только адресами доверенного прокси.
- `setup` выполняет миграции, создаёт группы и каталоги, собирает статику. Для обновления сделайте резервные копии, соберите новую версию и дождитесь завершения `setup`. PostgreSQL хранит состояние заявок и историю. Том файлов хранит байты. Для согласованного восстановления копируйте базу и файловый том при остановленной записи.
- ClamAV обновляет базы через FreshClam. Для закрытой инфраструктуры предоставьте утверждённое зеркало или настроенный внутренний ClamAV. Согласуйте лимит загрузки приложения 50 МиБ с конфигурацией `StreamMaxLength` и `MaxFileSize`. Сетевой доступ worker к источникам следует ограничить правилами вашей инфраструктуры в дополнение к проверкам URL.
- `/healthz/` проверяет работу HTTP. `/readyz/` проверяет PostgreSQL, Redis и каталоги. Docker отдельно проверяет готовность ClamAV. Для диагностики очереди смотрите `docker compose --env-file .env.compose logs worker scheduler clamav`, для заявки — карточку ИБ и аудит.
- Снимок совпадений с реестром создаётся при обработке. Изменения реестра применяются к следующим заявкам или при явном повторе обработки. Политика типа файла дополнительно проверяется при согласовании. Автоматическая антивирусная проверка снижает риск, решение о выдаче остаётся у ИБ.

## Существующая база

Перед переносом сделайте резервную копию PostgreSQL и файла окружения. Для старой базы используйте её реальные параметры подключения и прежний том, например через прежнее имя Compose-проекта, либо восстановите копию в новом проекте. Обычный первый запуск создаёт отдельные тома. Физические файлы старых установок переносите в согласованный корень хранилища отдельно.

Миграции сохраняют старые заявки и записи проверок. При развертывании старые ссылки автоматически не скачиваются. Заявки с имитацией проверки доступны для явного повтора обработки в очереди ИБ, если по ним ещё нет решения текущей версии. Файлы со старыми абсолютными путями поддерживаются только когда путь совпадает с их зоной внутри настроенного корня. При переносе на другой хост старый абсолютный путь может потребовать отдельной миграции данных. Старые файлы без установленного срока хранения оставляются оператору для разбора.

## Сквозная проверка

Выполняйте эти команды в отдельном проекте Compose. Вариант `--smoke` создаёт отдельную БД, отдельные секреты и порт 18080. Тест временно разрешает один внутренний адрес тестового HTTP-контейнера.

```sh
python3 scripts/init_compose_env.py --smoke .env.smoke
docker compose --env-file .env.smoke -p downloadscontrol-smoke -f docker-compose.yml -f deploy/compose.smoke.yml up --build -d --wait --wait-timeout 360
docker compose --env-file .env.smoke -p downloadscontrol-smoke -f docker-compose.yml -f deploy/compose.smoke.yml exec -T app python -m scripts.compose_smoke
docker compose --env-file .env.smoke -p downloadscontrol-smoke -f docker-compose.yml -f deploy/compose.smoke.yml exec -T -e TEST_POSTGRES=1 app python manage.py test --settings=config.test_settings --noinput
```

Тест подаёт заявку через Nginx, ждёт реальных Celery, PostgreSQL, Redis и ClamAV, согласует её от имени ИБ, проверяет выдачу правильных байтов владельцу и отказ другому пользователю, затем проверяет истечение срока и очистку. Для остановки используйте `down` с теми же аргументами проекта. Удаление тестовых томов выполняется отдельной командой `down --volumes` только для одноразового проекта проверки.
